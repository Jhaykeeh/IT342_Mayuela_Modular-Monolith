## 1. At 11:36:00 your request for BuyerRef "RO-7e235e44-e23c-4d29-bfd5-8d2107c431bf" (X-Request-Id RO-7e235e44-e23c-4d29-bfd5-8d2107c431bf) received a 503, but LegacySupply had already created PO-100228. Walk through exactly what your adapter did next, and explain why that did or did not result in a second order.

My adapter's `LegacySupplyClient` saw the HTTP 503 with code E-SYS-50 and treated it as retryable, logging `Request failed HTTP 503 (E-SYS-50), attempt 1/3 - retrying`. It backed off briefly and sent the exact same purchase-order request again, carrying the same BuyerRef and, crucially, the same X-Request-Id (RO-7e235e44-e23c-4d29-bfd5-8d2107c431bf), both of which were stored on the `supplier_orders` row when the reorder was first created. LegacySupply recognised the repeated X-Request-Id as an idempotent replay and returned the PO it had already made (PO-100228) instead of creating a new one. The adapter then stored PO-100228 as the acknowledgement, so the reorder was recorded exactly once. This did not result in a second order for two reasons: the request identifier is stable across retries (so LegacySupply could deduplicate it), and my `PendingOrderSenderJob` looks the BuyerRef up at LegacySupply before re-posting, adopting an existing PO rather than posting a competing one. LegacySupply's own report confirms the outcome: 0 duplicates, 2 chaos events, 2 safe replays.

## 2. PO-100219 (BuyerRef "RO-d6d162a6-74dc-498c-8b2d-5bfa95f14f5f") ended with StatusCode 90, which is not in the documentation. How did you work out what it means, and what does your system now do with the stock that will never arrive?

I did not invent a meaning for code 90. My `StatusMapper` only understands the documented codes 10 (accepted), 20 (picking), 30 (shipped) and 40 (delivered); anything else is mapped to the terminal status `UNKNOWN`. When the status poll returned 90 the log shows `PO PO-100219 -> UNKNOWN (legacy code 90)`, meaning the adapter deliberately refuses to guess. LegacySupply's /verify page later surfaced the truth by listing PO-100219 with StatusCode 90 under what it counts as a cancelled order ("Noticed a cancelled order: Met, 1 cancelled orders seen"), so 90 is LegacySupply's cancellation code. My system treats `UNKNOWN` as a non-delivery: it records the raw code in the `failure` column, it is excluded from polling, and it never restocks, so the 5 cases of NRQ-2742 that will never arrive are never added to inventory. Because `UNKNOWN` is not an open status, the low-stock sweeper placed a replacement reorder for P200 (PO-100220), which later reached DELIVERED and restocked the 30 units, so the shop still recovers from the cancelled order.

## 3. LegacySupply never tells you how long a session lasts. Measure your session lifetime from your own logs, state the number, and explain how your adapter decides when to sign in again.

From my probing logs a session token was still accepted at about 3 minutes 54 seconds after the token was issued, and the next requests were rejected with HTTP 401 E-AUTH-07 as "expired" somewhere between 4m00s and 4m33s. So the measured lifetime is approximately **4 minutes**. My adapter never assumes this number. It keeps a single session token and reuses it for every request, and it only signs in again on demand: either when there is no token at all, or when a request comes back with E-AUTH-03 (bogus session) or E-AUTH-07 (expired session). In those cases it discards the stale token, calls /auth/token once, and retries the original request with the fresh session. The lab logs show this in action, e.g. `Session rejected (E-AUTH-07); signing in again and retrying` followed by `Signed in to LegacySupply (session issued)` and a successful retry, and the /verify page records 11 sign-ins against 7 requests made with an expired session.

## 1. Tiangge may deliver the same event more than once. Describe how your application recognises an event it has already handled, where that knowledge is stored, and whether it survives a restart.

Duplicates are recognised with a durable claim in Postgres rather than anything held in memory: `ChannelStore.claimEvent(eventId)` runs `insert into channel_processed_event (event_id) values (:eventId) on conflict (event_id) do nothing`, and because `event_id` is that table's primary key the second delivery of `evt_ce628bfa41bb1b1a` inserts zero rows, so `claimEvent` returns false and `OrderIntake.createOnce` bails out before any order is created. Behind it sits a coarser second guard for the case where Tiangge redelivers the same *order* under a different event id: `channel_order_link.tiangge_order_id` is also a primary key, so `store.linkExists(orderId)` catches it and logs `Skipped duplicate event ... for Tiangge order ...` or `Tiangge order ... already has a link row; not creating a second order`. The knowledge survives restarts because it is a table rather than a field — I restarted the application several times during the lab and the rows in `channel_processed_event` and the cursor in `channel_cursor` were still there on the next boot, so the first event after every restart is checked against the same durable set instead of a freshly empty one. The claim also joins the intake transaction, so if order placement rolls back the claim rolls back with it and that event is retried rather than silently lost.

## 2. Pick one order your application accepted. Trace it from the feed to your database to the stock update you sent Tiangge, naming each class it passes through.

I traced TG-3ARKFD, a single line of `P100 x 6`. `FeedPoller.poll()`, a `@Scheduled(fixedDelay = 3_000)` task, read the position with `ChannelStore.readCursor()`, asked `TianggeClient.fetchFeed(cursor, limit)` for the next page, sorted it oldest-first by `seq` so events are applied in order, and dispatched the ORDER_PLACED event to `OrderIntake.onOrderPlaced`, which begins by calling `StockSync.hold()` so a stock publish can never overtake the decision. `OrderIntake.createOnce` claimed the event through `ChannelStore.claimEvent`, converted the line in `toItemRequests` into `OrderItemRequest("P100", 6)`, and called `edu.cit.mayuela.shop.OrderService.placeOrder(...)` — the identical method the React UI calls, so a marketplace order and a customer order share one path through the domain instead of having a privileged back door. A `CONFIRMED` result set the link state to ACCEPTED and the shop id to 38, and `ChannelStore.insertLink` wrote exactly one row to `channel_order_link`, still present as `TG-3ARKFD | 38 | ACCEPTED | P100x6`. The answer travels back through the durable outbox instead of inline: `Outbox.deliver` → `sendQuietly` → `send` invokes `TianggeClient.sendDecision("TG-3ARKFD", "ACCEPTED", 38L, null)`, which POSTs to `/orders/TG-3ARKFD/decision` carrying the reference `SO-38`, and only after that succeeds does `store.clearOutbox` blank the column and log `Sent DECISION for Tiangge order TG-3ARKFD (shopOrderId=38, state=ACCEPTED)`. Releasing the hold lets `StockSync.flushLocked` hand the dirty SKU to the single-threaded `channel-stock-publisher`, which re-reads the committed quantity through `InventoryService.getItem("P100")` and calls `TianggeClient.publishStock(...)` → `PUT /stock`, logging `Published stock to Tiangge: ...`; P100 stands at 18 in the `inventory` table today.

## 3. Your application now talks to two external systems with very different interfaces. Which of your modules know about Tiangge, which know about LegacySupply, and what would change if Tiangge were replaced by another marketplace?

Only `edu.cit.mayuela.channel` knows Tiangge exists: the entire HTTP surface is `TianggeClient` and the entire wire vocabulary is `TianggeBodies`, and no class outside that package imports either. Only `edu.cit.mayuela.supplier` knows LegacySupply exists, and the rest of the application reaches it exclusively through that module's own `SupplierGateway` and `OpenSupply` interfaces, with the XML quirks confined to `LegacyXml` and the undocumented status codes to `StatusMapper`. The domain modules `edu.cit.mayuela.shop` and `edu.cit.mayuela.inventory` know about neither system — they only ever see `OrderService` and `InventoryService`. That separation is enforced rather than merely intended: `ChannelArchitectureTest` applies three ArchUnit rules to the compiled classes, among them `noClasses().that().resideOutsideOfPackage("edu.cit.mayuela.channel..").should().dependOnClassesThat().resideInAPackage("edu.cit.mayuela.channel..")`, plus a rule that every non-interface type in the channel package must be package-private, which is why `ChannelStatus` is the channel's only public name. If Tiangge were replaced I would rewrite `TianggeClient` and `TianggeBodies` and repoint `channel.base-url`, because a different marketplace would also bring different event names, a different decision endpoint and possibly a different signing scheme — all of it contained in that one package. Because the ArchUnit rule forbids any inbound reference, that swap provably cannot ripple into `OrderService`, `InventoryService` or the supplier module; the only durable artefact needing re-mapping would be `channel_order_link`, since a new marketplace's order and event identifiers would have to be stored in its columns.
