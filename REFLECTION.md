# LAB 3 REFLECTION

Answers are written against evidence collected from the live LegacySupply service and this repository's own logs during the lab.

## 1. At 11:36:00 your request for BuyerRef "RO-7e235e44-e23c-4d29-bfd5-8d2107c431bf" (X-Request-Id RO-7e235e44-e23c-4d29-bfd5-8d2107c431bf) received a 503, but LegacySupply had already created PO-100228. Walk through exactly what your adapter did next, and explain why that did or did not result in a second order.

My adapter's `LegacySupplyClient` saw the HTTP 503 with code E-SYS-50 and treated it as retryable, logging `Request failed HTTP 503 (E-SYS-50), attempt 1/3 - retrying`. It backed off briefly and sent the exact same purchase-order request again, carrying the same BuyerRef and, crucially, the same X-Request-Id (RO-7e235e44-e23c-4d29-bfd5-8d2107c431bf), both of which were stored on the `supplier_orders` row when the reorder was first created. LegacySupply recognised the repeated X-Request-Id as an idempotent replay and returned the PO it had already made (PO-100228) instead of creating a new one. The adapter then stored PO-100228 as the acknowledgement, so the reorder was recorded exactly once. This did not result in a second order for two reasons: the request identifier is stable across retries (so LegacySupply could deduplicate it), and my `PendingOrderSenderJob` looks the BuyerRef up at LegacySupply before re-posting, adopting an existing PO rather than posting a competing one. LegacySupply's own report confirms the outcome: 0 duplicates, 2 chaos events, 2 safe replays.

## 2. PO-100219 (BuyerRef "RO-d6d162a6-74dc-498c-8b2d-5bfa95f14f5f") ended with StatusCode 90, which is not in the documentation. How did you work out what it means, and what does your system now do with the stock that will never arrive?

I did not invent a meaning for code 90. My `StatusMapper` only understands the documented codes 10 (accepted), 20 (picking), 30 (shipped) and 40 (delivered); anything else is mapped to the terminal status `UNKNOWN`. When the status poll returned 90 the log shows `PO PO-100219 -> UNKNOWN (legacy code 90)`, meaning the adapter deliberately refuses to guess. LegacySupply's /verify page later surfaced the truth by listing PO-100219 with StatusCode 90 under what it counts as a cancelled order ("Noticed a cancelled order: Met, 1 cancelled orders seen"), so 90 is LegacySupply's cancellation code. My system treats `UNKNOWN` as a non-delivery: it records the raw code in the `failure` column, it is excluded from polling, and it never restocks, so the 5 cases of NRQ-2742 that will never arrive are never added to inventory. Because `UNKNOWN` is not an open status, the low-stock sweeper placed a replacement reorder for P200 (PO-100220), which later reached DELIVERED and restocked the 30 units, so the shop still recovers from the cancelled order.

## 3. LegacySupply never tells you how long a session lasts. Measure your session lifetime from your own logs, state the number, and explain how your adapter decides when to sign in again.

From my probing logs a session token was still accepted at about 3 minutes 54 seconds after the token was issued, and the next requests were rejected with HTTP 401 E-AUTH-07 as "expired" somewhere between 4m00s and 4m33s. So the measured lifetime is approximately **4 minutes**. My adapter never assumes this number. It keeps a single session token and reuses it for every request, and it only signs in again on demand: either when there is no token at all, or when a request comes back with E-AUTH-03 (bogus session) or E-AUTH-07 (expired session). In those cases it discards the stale token, calls /auth/token once, and retries the original request with the fresh session. The lab logs show this in action, e.g. `Session rejected (E-AUTH-07); signing in again and retrying` followed by `Signed in to LegacySupply (session issued)` and a successful retry, and the /verify page records 11 sign-ins against 7 requests made with an expired session.
